# 两次导出目录对账

工作区本身只含 `sqlite-diffable` 工具源码, 没有业务数据库。本目录在其导出格式
(`.metadata.json` + `.ndjson`)之上, 提供一套可复现的对账脚手架: 先构造覆盖各类
情形的两次快照并导出成目录, 再只读导出目录完成身份三分类与跨表订单核对。

## 数据模型

| 表 | 关键列 | 作用 |
| --- | --- | --- |
| `customers` | `cust_id`(主键), `id_no`, `dept`, `status` | 客户主表, `id_no` 为自然人身份锚点 |
| `accounts` | `account_no`(主键), `cust_id`, `id_no`, `opened_at`, `status` | 开户记录, 含开关户状态 |
| `identity_map` | `biz_id`(主键), `id_no`, `cust_id` | 业务身份映射, `cust_id` 为空表示已与编号解绑 |
| `orders` | `order_no`(主键), `cust_id`, `account_no` | 订单, 同时挂客户编号与账户 |

## 判定口径

身份锚点强弱: **客户主表证件号 > 未关闭账户证件号 / 仍绑定的业务身份映射 >
已关闭账户与历史映射(仅残留, 不单独证明延续)**。

- **可确认延续**: 客户主表证件号两版一致, 且活跃账户/映射仍锚定同一证件号。
  部门、电话等变化不改变自然人身份(如客户 1 的 A→B 调动)。
- **可确认更替**: 主表证件号变为另一个非空值, 且活跃锚点与旧证件号完全断裂
  (旧账户关闭、旧映射解绑、按新证件重新开户/建映射); 也包括编号消失与纯新增编号。
- **待确认**: v2 主表证件号缺失, 旧证件号只剩关闭态/历史态证据, 又没有第二个
  自然人的直接证据。此时两种解释都成立, 报告原样列出, 交客服补件:
  1. 部门调动/同一人延续——补 v2 证件号与旧证件号一致即可确认;
  2. 删号重用/新旧更替——提供新客户开户证件, 证明与旧客户为不同人。

订单核对规则: 同一笔订单经"账户证件号 + 客户主表证件号"链路只能收敛到**单个**
证件号; 出现多个证件号即身份冲突, 不能同时给两个客户作证。订单所挂账户登记的
证件号作为"账户锚定", 给出推荐归属; 两版挂账账户本身已换人、无法判定时,
冻结对外证明, 转人工凭原始凭证裁定。

## 运行

```bash
# 1. 构造示例两次快照并导出(真实使用时替换为自己的两个导出目录即可)
python -m reconcile.fixture

# 2. 对账(默认读 data/export_v1 与 data/export_v2, 写 report/)
python -m reconcile.report

# 也可对任意两个真实导出目录运行
python -m reconcile.report /path/to/export_v1 /path/to/export_v2 -o /path/to/report
```

输出:

- `report/reconciliation_report.md`: 给客服看的中文对账报告
- `report/reconciliation.json`: 机读结果(三分类 + 每笔订单判定与处置建议)

测试: `python -m pytest tests/test_reconcile.py`
